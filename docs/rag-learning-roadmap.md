# CRM 项目 RAG 学习与实战路线

## 1. 文档目标

本路线以智能营销管理系统作为持续实验场，不额外建设脱离业务的演示项目。学习过程围绕产品知识、解决方案、客户案例、销售话术、线索分析、客户深度总结和智能体助手等真实场景展开。

最终目标不是只会调用 Embedding 模型和向量数据库，而是能够独立完成以下工作：

- 设计并实现文档解析、清洗、切分、向量化和索引版本管理。
- 根据问题特点选择关键词检索、向量检索、混合检索和精排方案。
- 建立可复现的离线评测集，用数据判断每次调整是否有效。
- 构建带引用、可拒答、可追踪且具备权限隔离的 RAG 应用。
- 能够定位错误发生在解析、召回、排序、上下文构建还是答案生成阶段。
- 将 RAG 作为标准工具或工作流节点接入 LangGraph 智能体。

## 2. 当前项目基础

CRM 当前已经具备以下能力：

- 文档导入、解析、清洗和异步入库。
- 文档切分、Embedding 生成及分片元数据存储。
- 基于原始文件 Hash 和标准化内容 Hash 的重复判断。
- 文档不可变版本、活动版本切换和 `index_version` 隔离。
- Elasticsearch 关键词召回。
- Milvus 向量召回。
- 向量、关键词及数据库候选结果的加权 RRF 融合。
- 索引代次和蓝绿索引重建基础设施。
- Python AI Runtime 中的知识库混合检索工具。
- 线索分析、客户深度总结和智能体助手等 RAG 使用场景。

当前重点不再是继续堆叠中间件，而是补齐以下质量闭环：

- Golden Dataset 和稳定基线。
- 召回、排序和答案质量指标。
- 真正的 Cross-Encoder 精排。
- 结构感知切分、父子分片和上下文组装。
- 引用、拒答、幻觉检测和权限验证。
- Langfuse 实验对比及线上质量观测。

需要明确：当前 RRF 解决的是多路结果融合排序，不等同于使用模型对“问题与分片”重新计算相关性的精排。

## 3. 学习方法

每一阶段都采用相同的实验闭环：

```text
学习原理
  -> 提出一个可验证假设
  -> 只修改一个变量
  -> 使用同一评测集运行实验
  -> 对比质量、耗时和资源消耗
  -> 记录结论
  -> 决定保留、回退或继续调整
```

禁止同时修改 Embedding 模型、Chunk 大小、召回数量、精排模型和提示词，否则无法判断质量变化来自哪个变量。

建议时间分配：

- 20%：学习原理和阅读官方资料。
- 60%：在 CRM 真实链路中实现和实验。
- 20%：评测、复盘和沉淀结论。

按每周 8 至 12 小时设计，预计 8 周完成。集中投入时可以压缩为 4 周，但阶段顺序不变。

## 4. 第零阶段：建立评测基线

### 4.1 学习目标

- 理解为什么没有评测集就无法调优 RAG。
- 区分检索评测、答案评测和业务评测。
- 建立可以重复执行的基线测试。

### 4.2 建议目录

```text
crm-ai-runtime/evals/rag/
├── datasets/
│   └── golden_rag.jsonl
├── run_retrieval_eval.py
├── run_answer_eval.py
└── reports/
```

### 4.3 Golden Dataset 组成

第一版建议准备 100 条真实问题：

| 类型 | 数量 | 示例方向 |
|---|---:|---|
| 产品明确事实 | 30 | 部署方式、支持能力、适用范围 |
| 产品定位与能力 | 20 | 产品解决什么问题、适合什么客户 |
| 解决方案 | 15 | 不同行业和场景的产品组合 |
| 销售话术 | 10 | 首次触达、异议处理、成交推进 |
| 跨文档综合 | 10 | 同时依赖产品、方案和案例 |
| 产品对比 | 5 | 不同产品边界和组合方式 |
| 无答案问题 | 5 | 知识库中明确不存在的信息 |
| 隔离验证 | 5 | 跨租户、跨产品和无权限数据 |

建议数据格式：

```json
{
  "id": "openocta-001",
  "question": "OpenOcta适合解决什么问题？",
  "productId": "产品编号",
  "expectedChunkIds": ["目标分片编号"],
  "expectedFacts": ["企业级智能体统一管理", "权限与审计"],
  "shouldAnswer": true,
  "difficulty": "MEDIUM",
  "type": "SEMANTIC"
}
```

### 4.4 基线指标

检索指标：

- `Recall@5`、`Recall@10`：正确分片是否进入候选结果。
- `MRR@10`：第一个正确结果是否足够靠前。
- `nDCG@10`：多个相关结果的整体排序质量。
- 无答案问题的误召回率。
- 跨租户和跨产品数据泄漏数，目标必须为零。
- 检索 P50、P95 耗时。

答案指标：

- 事实正确性。
- 忠实度，答案是否完全来自给定证据。
- 问题相关性。
- 引用准确率和引用覆盖率。
- 应当拒答时的拒答准确率。
- 首字延迟、总耗时和 Token 使用量。

### 4.5 阶段产物

- 第一版 `golden_rag.jsonl`。
- 当前线上参数的检索基线报告。
- 当前模型和索引版本的固定实验编号。

## 5. 第一阶段：文档解析、清洗和切分

### 5.1 学习内容

- PDF、Word、HTML、Markdown 和纯文本解析。
- 页眉页脚、目录、空白、乱码、重复段落和表格清洗。
- 固定长度切分、递归切分、标题感知切分和语义切分。
- Chunk 大小、Overlap、上下文完整性和召回精度之间的关系。
- 父子分片和 Small-to-Big Retrieval。
- 标题、章节、页码、产品、版本、权限等 Metadata 设计。

### 5.2 CRM 实验

对同一批产品文档分别使用以下参数入库：

- 500 字符，Overlap 80。
- 900 字符，Overlap 120。
- 1500 字符，Overlap 200。
- 按标题、段落和列表结构切分。

每组实验都使用同一评测集计算 Recall、MRR、答案忠实度和上下文 Token 数。

重点验证：

- 中文标点是否真正参与断句。
- 表格中的字段和值是否仍保持对应关系。
- 标题是否被写入每个子分片的 Metadata 或正文前缀。
- 跨页内容是否被错误拆开。
- 同一内容重复导入时是否跳过解析和向量化。

### 5.3 阶段产物

- 文档清洗规则清单。
- 分片调试视图。
- 不同 Chunk 策略的实验对比报告。
- 面向产品资料的默认切分策略。

## 6. 第二阶段：关键词检索和向量检索

### 6.1 学习内容

- 倒排索引、词频、逆文档频率和 BM25 基本原理。
- Embedding、余弦相似度、点积和欧氏距离。
- ANN、HNSW、召回率和搜索延迟之间的关系。
- TopK、过滤条件和候选集大小。
- 中文分词、产品专有名词、缩写和同义词处理。

### 6.2 CRM 实验

分别建立并比较：

```text
Elasticsearch BM25 Only
Milvus Dense Vector Only
```

重点观察：

- 产品名称、版本号和专有名词是否更适合 BM25。
- 用户口语化描述、同义表达是否更适合向量检索。
- 产品、租户、状态和活动版本过滤是否在召回前生效。
- 当前 Embedding 服务实际暴露的是 Dense 能力，还是同时支持 Sparse 和 Multi-Vector。

### 6.3 阶段产物

- BM25 与 Dense Vector 的适用边界说明。
- Elasticsearch 和 Milvus 单路召回基线。
- Embedding 模型、维度、距离类型和索引参数记录。

## 7. 第三阶段：混合检索和融合排序

### 7.1 学习内容

- 为什么 BM25 分数与向量相似度不能直接相加。
- Reciprocal Rank Fusion 的原理和 `rrfK` 参数。
- Weighted Fusion 的分数归一化问题。
- 候选集数量、最终 TopK 和最小分数阈值。
- 多查询改写、关键词扩展和查询路由。

### 7.2 CRM 实验

比较以下方案：

```text
BM25 Only
Dense Vector Only
BM25 + Dense + RRF
BM25 + Dense + 加权融合
```

建议增加检索调试能力，输入一个问题后展示：

- Elasticsearch 排名和 BM25 分数。
- Milvus 排名和向量分数。
- RRF 融合分数和最终排名。
- 命中的产品、文档、版本和分片。
- 每一路召回耗时。
- 最终分片入选原因。

### 7.3 阶段产物

- 可调节候选数、权重、`rrfK` 和 TopK 的检索实验工具。
- 四种召回方案在同一 Golden Dataset 上的对比报告。
- 面向 CRM 产品知识的默认混合检索参数。

## 8. 第四阶段：精排和上下文构建

### 8.1 学习内容

- 融合排序与模型精排的区别。
- Cross-Encoder 对问题和分片进行联合相关性评分的原理。
- 候选召回、精排数量和计算成本的平衡。
- 相邻分片扩展、父分片回溯、分片去重和结果多样性。
- 上下文 Token 预算和信息密度。

### 8.2 推荐链路

```text
Elasticsearch Top20 + Milvus Top20
                  ↓
                RRF Top20
                  ↓
       Cross-Encoder Reranker
                  ↓
                 Top5
                  ↓
         父分片或相邻分片扩展
```

### 8.3 CRM 实验

逐项比较：

- 候选数量：10、20、50。
- 精排输出：3、5、8。
- 最低相关性阈值。
- 同一文档最大入选分片数。
- 是否扩展父分片和相邻分片。
- 精排前后 Recall、MRR、nDCG、答案质量和总耗时。

### 8.4 阶段产物

- 独立 Reranker 服务或标准适配层。
- 统一的上下文构建器。
- 精排前后质量和耗时对比报告。

## 9. 第五阶段：答案生成、引用和防幻觉

### 9.1 学习内容

- Grounded Generation。
- 结构化上下文和提示词边界。
- 引用定位、引用覆盖和来源可信度。
- 无答案检测和拒答策略。
- Prompt Injection、恶意文档和数据污染防护。
- 答案生成失败与检索失败的区分。

### 9.2 标准答案结构

面向销售和客服的知识回答至少包含：

- 直接结论。
- 支撑结论的关键事实。
- 对应产品或解决方案。
- 来源文档和可访问链接。
- 信息不足时的明确说明。

不得把原始检索 JSON 或大段分片原文直接返回给销售人员。

### 9.3 阶段产物

- 带引用的产品知识问答。
- 无答案拒答规则。
- 引用准确率和忠实度评测。
- 恶意文档和越权检索测试集。

## 10. 第六阶段：2-Step、Hybrid 和 Agentic RAG

不同 CRM 场景应使用不同架构，不能全部交给智能体自由决策。

| 场景 | 推荐架构 | 原因 |
|---|---|---|
| 产品问答、FAQ | 2-Step RAG | 固定检索后回答，速度快且行为稳定 |
| 线索分析 | LangGraph Hybrid RAG | 需要业务上下文、检索、校验和结构化输出 |
| 客户深度总结 | LangGraph Hybrid RAG | 需要组合 CRM 数据、跟进记录和知识库 |
| 通用智能体助手 | Agentic RAG | 由模型选择知识库、CRM、MCP 或公开搜索工具 |

### 10.1 线索分析推荐工作流

```text
读取线索上下文
  -> 识别行业、问题和产品意向
  -> 生成知识库查询
  -> 混合召回与精排
  -> 校验证据是否充分
     -> 不充分：改写查询并最多重试一次
     -> 充分：继续生成
  -> 生成销售分析
  -> 校验引用和结构化结果
  -> 返回最终结论
```

### 10.2 通用助手推荐流程

通用助手继续使用标准 Agent，并将知识库检索作为 Tool 动态调用。对于必须检索才能作答的问题，在场景提示词或 Skill 中明确检索约束；对于复杂且需要确定执行顺序的任务，使用显式 StateGraph 编排。

### 10.3 阶段产物

- 2-Step 产品知识客服。
- Hybrid 线索分析图。
- Hybrid 客户深度总结图。
- Agentic 智能体助手知识库工具调用。

## 11. 第七阶段：Langfuse 评测和线上观测

### 11.1 实验管理

将 `golden_rag.jsonl` 导入 Langfuse Dataset。以下任何变量发生变化时，都创建新的 Experiment：

- Embedding 模型或版本。
- Chunk 策略版本。
- Elasticsearch 和 Milvus 候选数量。
- RRF 参数和各路权重。
- Reranker 模型和阈值。
- 最终 TopK。
- Prompt 和模型版本。

### 11.2 Trace 内容

每次 RAG 调用至少记录：

- Trace ID、租户、用户和场景。
- 原始问题、规范化问题和改写后的查询。
- 过滤条件和权限范围。
- 每一路召回结果、分数和耗时。
- 融合和精排前后的结果。
- 文档版本、索引版本和模型版本。
- 最终上下文和引用。
- 模型输入输出 Token。
- 首字延迟和总耗时。
- 用户反馈和人工评分。

### 11.3 离线与在线闭环

```text
线上 Trace 发现失败案例
  -> 人工确认正确答案和相关文档
  -> 加入 Golden Dataset
  -> 修改一个变量并运行 Experiment
  -> 对比质量、耗时和成本
  -> 达到门槛后发布
  -> 继续观察线上指标
```

### 11.4 阶段产物

- Langfuse RAG Trace。
- Dataset 和多次 Experiment 对比。
- 线上质量看板。
- 发布前自动回归门槛。

## 12. 第八阶段：生产级治理

### 12.1 必备能力

- 租户、产品、部门、角色和文档权限隔离。
- 文档版本与索引版本一致性。
- 重复入库幂等处理。
- 蓝绿索引重建和失败回退。
- Embedding、ES、Milvus 和 Reranker 超时与重试。
- 查询缓存和热点问题缓存。
- 并发控制、限流和熔断。
- 敏感信息脱敏和日志保留策略。
- 文档删除后的索引清理验证。
- 模型、提示词、索引和评测结果可追溯。

### 12.2 暂缓内容

在基础 RAG 没有稳定评测结果前，暂不优先投入：

- GraphRAG。
- 多智能体协作检索。
- 大量反思和循环检索。
- 为了追求框架统一而重写已经稳定的知识服务。
- 没有评测依据的模型微调。

只有当评测数据证明普通混合 RAG 无法解决多跳关系、跨实体推理等问题时，再引入 GraphRAG。

## 13. 最终综合验收项目

完成以下四个真实业务功能，作为掌握 RAG 的最终证明。

### 13.1 产品知识客服

- 回答产品定位、能力、部署方式和常见问题。
- 所有关键事实带引用。
- 知识库不存在的信息明确拒答。

### 13.2 线索产品匹配

- 根据线索行业、需求、风险和购买意向检索产品资料。
- 推荐对应产品、解决方案和客户案例。
- 将证据转化为销售可执行的下一步动作。

### 13.3 客户深度总结

- 组合客户资料、历史跟进、商机、产品和知识库。
- 识别客户当前阶段、风险、异议和推荐方案。
- 生成下一次跟进计划和推荐话术。

### 13.4 个性化营销话术

- 结合客户画像、产品知识和营销 Skill。
- 支持首次触达、需求探查、异议处理和成交推进。
- 不得虚构公司能力、案例、价格和承诺。

## 14. 学习完成标准

达到以下标准，可以认为已经具备独立设计和落地企业级 RAG 的能力：

- 能解释 BM25、Dense Retrieval、ANN、RRF 和 Cross-Encoder 的作用与边界。
- 能根据文档结构选择切分策略，而不是只调整固定字符数。
- 能用 Recall、MRR、nDCG、忠实度和引用准确率评估系统。
- 能通过 Trace 定位一次错误回答的具体失败阶段。
- 能为不同业务场景选择 2-Step、Hybrid 或 Agentic RAG。
- 能实现带权限过滤、版本隔离、引用和拒答的完整链路。
- 能通过固定评测集证明一次优化确实有效。
- 能处理线上数据漂移、失败案例回流和持续评测。

排查错误回答时，应按照以下顺序定位：

```text
文档是否正确解析
  -> 文档是否正确清洗
  -> 分片边界是否合理
  -> Metadata 和权限是否正确
  -> Embedding 是否有效
  -> 目标分片是否被召回
  -> 融合排序是否正确
  -> 精排是否保留正确证据
  -> 上下文是否被截断或污染
  -> 模型是否忠于上下文
  -> 引用是否映射到真实来源
```

## 16. 推荐实施顺序

近期严格按照以下顺序推进：

1. 创建第一版 Golden Dataset。
2. 完成检索评测脚本并记录当前基线。
3. 验证中文解析、清洗和切分质量。
4. 对比 BM25、Dense 和当前 RRF 混合检索。
5. 接入真正的 Cross-Encoder 精排。
6. 建立统一上下文构建、引用和拒答机制。
7. 将线索分析和客户深度总结接入 Hybrid RAG。
8. 接入 Langfuse Dataset、Experiment 和线上 Trace。
9. 建立发布前 RAG 回归门槛。
10. 根据失败案例决定是否引入查询改写、父子分片或更高级架构。
