# 从能用到生产级：RAG 优化实战系列大纲

## 一、系列定位

本系列不单独搭建脱离业务的 RAG 示例，而是以“智能营销管理系统”为持续案例，拆解一套 RAG 系统从文档入库、切分、索引、查询、召回、精排、上下文构建到评测、治理和千万级扩展的完整链路。

系列重点不是介绍某个框架的 API，而是回答以下问题：

- 一份业务文档如何稳定、可追踪地进入知识库？
- 文档应该怎么切，才能兼顾召回精度和上下文完整性？
- Elasticsearch、Milvus 和数据库应该如何配合？
- 用户的问题不适合直接检索时，查询应该怎样改写和拆解？
- RRF、Reranker 和上下文构建分别解决什么问题？
- 如何让答案带引用、会拒答，并且不泄露其他租户的数据？
- 如何通过评测证明一次优化真正有效？
- 当文档和向量达到千万甚至亿级时，系统架构应该怎样调整？
- RAG 如何与 CRM 数据、工具调用和智能体工作流结合？

## 二、系列名称

主标题：

> 从能用到生产级：RAG 优化实战

副标题：

> 基于智能 CRM 项目，拆解文档、检索、精排、评测与规模化

## 三、目标读者

- 正在开发企业知识库、智能客服或 AI 助手的开发者。
- 已经完成基础 RAG，但检索效果不稳定的开发者。
- 希望将 RAG 接入 CRM、ERP、客服和内部业务系统的团队。
- 需要考虑多租户、文档版本、权限、审计和生产运维的架构人员。

## 四、系列主线

```text
文档进入系统
  → 文档清洗与身份识别
  → 文档版本与异步入库
  → 结构感知切分
  → Embedding 与多路索引
  → 查询理解与改写
  → BM25 + Dense 混合召回
  → RRF 融合与模型精排
  → 上下文组装与引用
  → 离线评测与线上观测
  → 蓝绿索引与规模化
  → CRM 智能体业务闭环
```

## 第 9 讲：千万级文档的 RAG 架构

状态：待写

推荐标题：

> 千万级 RAG 怎么做？先别急着讨论向量数据库

### 本讲首先需要澄清

“千万级文档”与“千万级向量”不是同一个规模。

```text
1000 万份文档
× 每份文档平均 20 个 Chunk
= 2 亿条向量
```

容量设计前必须明确：

- 文档数量。
- Chunk 和向量数量。
- 向量维度。
- Metadata 大小与过滤基数。
- 每日新增、更新和删除量。
- 查询 QPS。
- P95 延迟目标。
- 租户数量与大租户占比。

### 主要内容

#### 存储与分区

- PostgreSQL 保存元数据、版本和任务状态。
- Elasticsearch Shard 与索引生命周期。
- Milvus Collection、Partition 和 Segment 规划。
- 按租户、业务、产品或时间分区。
- 大租户独立索引，小租户共享索引。
- 热数据、温数据和冷数据分层。

#### 离线写入

- 批量解析、批量 Embedding 和批量写入。
- 消息队列削峰与消费并发。
- 幂等、断点续跑和失败队列。
- 增量更新和删除传播。
- 写入背压与资源隔离。

#### 在线查询

- 查询路由与租户路由。
- Metadata 预过滤。
- ANN 索引参数与召回率。
- 候选集大小和精排成本。
- 查询 Embedding 缓存和热门问题缓存。
- 超时、限流、熔断与降级。

#### 运维与成本

- 索引构建速度和容量预估。
- 在线查询与离线构建资源隔离。
- 数据删除与索引清理验证。
- 扩容、缩容、迁移和灾难恢复。
- 每百万次检索和每百万条向量的成本估算。

### 建议文章结构

1. 先把“规模”换算成向量数量和资源需求。
2. 千万级系统的逻辑分层。
3. 数据如何分区、路由和隔离。
4. 离线入库如何提高吞吐。
5. 在线查询如何保证延迟。
6. 全量重建如何避免影响线上流量。
7. 什么时候应该拆 Collection 或独立集群。
8. 容量规划与压测清单。

### 可拆分方案

如果篇幅过长，本讲可以拆为两篇：

- 第 9A 讲：千万级文档的解析、Embedding 与索引构建。
- 第 9B 讲：千万级向量的在线检索、路由与性能优化。

> RAG 如何接入 CRM 智能体：从知识问答到销售行动

### 本讲解决的问题

- 为什么企业 RAG 不应该只做一个聊天窗口？

- 智能体什么时候调用知识库，什么时候调用 CRM 工具？
- 如何把检索证据转换成下一步销售行动？

### 项目结合点

- `KnowledgeSearchTool`。
- `CustomerQueryTool`。
- `LeadQueryTool`。
- `FollowupQueryTool`。
- 线索分析智能体。
- 客户深度总结智能体。
- AI 营销助手。
- Agent Runtime、Skill 和 MCP 扩展能力。

### 场景与架构选择

| 业务场景 | 推荐架构 | 原因 |
| --- | --- | --- |
| 产品问答与 FAQ | 2-Step RAG | 行为稳定、响应速度快 |
| 线索分析 | Hybrid RAG | 需要组合线索数据、知识检索和结构化输出 |
| 客户深度总结 | Hybrid RAG | 需要客户、跟进、商机和知识库共同参与 |
| 通用营销助手 | Agentic RAG | 需要动态选择 CRM、知识库、MCP 或公开搜索工具 |

### CRM 示例流程

## 六、每篇文章的统一写作结构

后续正式写作时，每一讲统一按照以下结构组织：

1. 用一个真实业务问题开场。
2. 解释常见实现为什么会失败。
3. 给出必要的基础原理。
4. 拆解当前 CRM 项目的实现。
5. 指出当前方案的优点和不足。
6. 给出可以执行的优化方案。
7. 提供关键代码、配置或伪代码。
8. 设计一组可验证的对比实验。
9. 总结常见误区和上线检查项。
10. 引出下一讲的问题。

## 七、系列写作原则

- 不为了堆概念而堆概念，每一项技术都要说明它解决的具体问题。
- 明确区分项目“当前已经实现”和“下一阶段准备实现”的能力。
- 不把 RRF 描述成模型精排，不把向量检索描述成万能方案。
- 所有优化尽量配套评测指标，不使用“感觉效果更好”作为结论。
- 所有示例优先使用 CRM 产品知识、线索分析、客户总结和销售跟进场景。
- 代码示例只保留关键逻辑，避免整段复制项目源码。
- 涉及千万级规模时，先说明文档数、Chunk 数、向量数、QPS 和延迟目标。
- 安全相关内容必须覆盖租户隔离、活动版本校验、权限过滤和审计追踪。
