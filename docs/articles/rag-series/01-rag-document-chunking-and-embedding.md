# RAG 文档切分怎么优化？从一份 CRM 销售 SOP 讲清楚 Chunk 与向量化

> 系列：从能用到生产级——RAG 优化实战  
> 第 1 讲：文档切分与向量化  
> 项目案例：智能营销管理系统

## 前言

做 RAG 时，我们通常会把注意力放在大模型和向量数据库上：

- 用哪个 Embedding 模型？
- Milvus 和 Elasticsearch 怎么选？
- TopK 设置成多少？
- 最后用哪个大模型回答？

但很多“明明知识库里有答案，系统就是搜不到”的问题，根源并不在模型，也不在向量数据库，而是在更前面的一步：**文档切分**。

一份完整文档不能原封不动地丢给模型。我们需要先把它拆成一个个小片段，再为每个片段生成向量。用户提问时，系统也会把问题转换成向量，然后寻找最相似的文档片段。

换句话说：

> 大模型最后能看到什么，很大程度上取决于我们最开始把文档切成了什么样。

这篇文章不讲太多抽象概念，而是结合智能 CRM 项目中的知识库实现，从零说明三个问题：

1. 文档切分为什么会影响搜索结果？
2. 一份业务文档到底应该怎么切？
3. 切分完成后，文本又是如何变成向量的？

---

## 一、先用一句话理解 RAG

RAG 的全称是 Retrieval-Augmented Generation，中文一般叫“检索增强生成”。

名字看起来复杂，其实可以把它理解成一次开卷考试：

```text
用户提出问题
  → 系统先去知识库找资料
  → 把找到的资料交给大模型
  → 大模型根据资料组织答案
```

大模型不是直接记住企业所有知识，而是在回答之前临时查资料。

例如销售人员在 CRM 中问：

> 什么情况下可以把一条线索转成客户？

系统会先从知识库检索“线索评分标准”“推荐状态”和“客户转化条件”等内容，再让模型根据这些证据回答。

这个过程看上去很自然，但计算机面对的不是“整篇文档”，而是一组提前切好的 Chunk。

完整链路如下：

```text
销售 SOP 文档
  → 清洗文本
  → 切成多个 Chunk
  → 每个 Chunk 生成 Embedding
  → 写入 Milvus 和 Elasticsearch

用户问题
  → 生成 Query Embedding
  → 检索相似 Chunk
  → 把 Chunk 交给大模型
  → 生成答案
```

所以，RAG 的检索单位通常不是文档，而是 Chunk。

## 二、为什么不能直接向量化整篇文档

假设我们有一份两万字的《线索评估与跟进 SOP》，里面包含：

- 首次处理方法
- 线索评分标准
- 推荐状态说明
- 下一步动作模板
- 风险检查规则

如果直接把整篇文档生成一个向量，会遇到三个问题。

### 1. 一篇文档只有一个向量，表达不了所有主题

Embedding 会尝试把整篇内容压缩成一组数字。

文档同时讲线索评分、客户转化、跟进动作和风险规则，这个向量只能表达一个模糊的“线索管理”主题，很难准确表示某一条具体规则。

用户问“什么时候应该预约需求访谈”，真正需要的是“下一步动作模板”中的一个小段落，而不是整篇 SOP。

### 2. 大文档容易超过模型输入限制

Embedding 模型有输入长度限制。文档过长时，要么调用失败，要么只能截断。

如果关键答案刚好在被截掉的后半部分，即使文档已经入库，也永远检索不到。

### 3. 返回整篇文档会浪费大模型上下文

即使能够检索整篇文档，把两万字全部交给大模型，也会增加 Token 消耗和响应时间。

更麻烦的是，无关内容越多，大模型越难抓住真正有用的证据。

因此，我们需要先把文档拆成语义相对完整的小块。

---

## 三、Chunk 不是越小越好

很多人第一次优化 RAG，会直接把 Chunk 调小：

```text
原来每块 1000 字
搜不准
那就改成 300 字
```

Chunk 变小以后，内容确实更集中，但上下文也可能被切没。

来看一个 CRM 中的例子。

原文：

```text
## 线索评分参考

- 需求明确：客户能够描述当前问题、期望效果或计划替换的现有方案，可增加评分。
- 关键角色：联系人是业务负责人、技术负责人、采购参与者或能够引荐决策人，可增加评分。
- 时间计划：客户存在三个月以内的选型、测试或采购计划，可提高优先级。
- 预算信息：预算已确认或存在明确预算申请流程，可提高转化建议置信度。
- 信息不足：仅有姓名和联系方式，没有需求、角色、预算及时间计划时，不建议直接转客户。
```

如果 Chunk 太小，可能被切成：

```text
Chunk 1：
## 线索评分参考
- 需求明确：客户能够描述当前问题……

Chunk 2：
- 关键角色：联系人是业务负责人……
- 时间计划：客户存在三个月以内的选型……

Chunk 3：
- 预算信息：预算已确认……
- 信息不足：仅有姓名和联系方式……
```

Chunk 2 和 Chunk 3 已经失去了“线索评分参考”这个标题。

当用户搜索“线索转客户需要满足什么条件”时，单独看到“预算信息”或者“信息不足”，检索模型未必知道它们属于线索评分规则。

但 Chunk 太大也不好。

如果把整份 SOP 放进同一个 Chunk，“什么时候转客户”会和首次触达、演示安排、风险检查等大量内容混在一起，语义又会变得不集中。

所以，Chunk 大小实际上是在平衡两件事：

```text
Chunk 越小：主题更集中，但上下文更容易丢失
Chunk 越大：上下文更完整，但噪声和 Token 更多
```

不存在适用于所有项目的“最佳 Chunk 大小”。正确答案只能通过自己的文档和问题集测出来。

## 四、当前 CRM 项目是怎么切文档的

当前项目中的基础切分器是 `KnowledgeTextSplitter`，默认参数为：

```properties
crm.knowledge.chunk.max-chars=900
crm.knowledge.chunk.overlap-chars=120
```

意思是：

- 每个 Chunk 最多约 900 个字符；
- 相邻 Chunk 重叠约 120 个字符；
- 如果 900 字符附近存在换行，优先在换行处切开；
- 如果没有合适换行，则尝试在句号、问号、感叹号或分号处切开；
- 实在找不到自然边界，才按照最大长度截断。

核心思路可以简化成下面的伪代码：

```java
while (当前位置 < 文本长度) {
    int 暂定结束位置 = 当前位置 + 最大字符数;

    // 优先寻找段落边界
    int 实际结束位置 = 查找附近的换行位置();

    // 没有合适换行时，再寻找句子边界
    if (没有找到段落边界) {
        实际结束位置 = 查找附近的句号或分号();
    }

    保存当前分片();

    // 向前回退一小段，保留上下文重叠
    当前位置 = 实际结束位置 - 重叠字符数;
}
```

在切分之前，系统还会进行基础清洗：

- 把不间断空格替换成普通空格；
- 合并连续空格和制表符；
- 合并过多空行；
- 清除首尾空白。

这套方案的优点很明确：

- 实现简单，运行稳定；
- 支持中文标点；
- 不容易从一句话中间截断；
- 通过 Overlap 减少边界信息丢失；
- 非常适合作为第一版基线。

但它目前只认识“字符、换行和标点”，还不真正理解下面这些文档结构：

- Markdown 标题层级；
- 编号列表；
- 表格；
- 代码块；
- FAQ 的问题和答案；
- 一个章节与子章节之间的关系。

因此，当前实现是一个可用的起点，但还不是最终形态。

## 五、Overlap 到底有什么用

Overlap 就是让相邻两个 Chunk 重复一部分内容。

假设原文为：

```text
客户已经表达明确需求，并计划在三个月内完成选型。
销售应进一步确认预算、决策链和测试标准。
确认后可以准备对应产品材料并安排演示。
```

如果刚好在第一句后切开：

```text
Chunk A：
客户已经表达明确需求，并计划在三个月内完成选型。

Chunk B：
销售应进一步确认预算、决策链和测试标准。
确认后可以准备对应产品材料并安排演示。
```

Chunk B 里的“确认后”缺少前提。系统只召回 Chunk B 时，大模型可能不知道要确认什么。

增加重叠后：

```text
Chunk B：
客户已经表达明确需求，并计划在三个月内完成选型。
销售应进一步确认预算、决策链和测试标准。
确认后可以准备对应产品材料并安排演示。
```

语义就完整多了。

但 Overlap 也不能无限加大。重叠过多会导致：

- 向量库里出现大量重复内容；
- 同一个答案命中多个几乎相同的 Chunk；
- TopK 被重复结果占满；
- Embedding 和存储成本增加；
- 大模型收到重复上下文。

经验上，Overlap 可以先从 Chunk 长度的 `10%～20%` 开始测试，但不要把这个比例当作固定标准。

当前项目使用 `900 + 120`，重叠比例约为 `13%`，属于比较稳妥的基线。

## 六、下一步：从固定长度升级到结构感知切分

真正适合企业知识库的切分方式，应该先理解文档结构，再考虑字符数量。

推荐处理顺序如下：

```text
识别文档类型
  → 清洗页眉、页脚和重复内容
  → 解析标题、段落、列表、表格和代码块
  → 先按结构形成语义块
  → 小块合并
  → 大块递归拆分
  → 补充标题路径和 Metadata
  → 生成父子分片
```

### 1. 标题不要和正文分家

假设原文是：

```text
## 风险检查

不得将公开搜索摘要当成已确认事实；不得编造联系人职位、公司规模、采购预算或成交日期。
```

不要只向量化正文：

```text
不得将公开搜索摘要当成已确认事实……
```

推荐构造专门用于向量化的文本：

```text
线索评估与跟进 SOP > 风险检查

不得将公开搜索摘要当成已确认事实；不得编造联系人职位、公司规模、采购预算或成交日期。
```

这样用户搜索“线索分析有哪些风险规则”时，更容易召回这段内容。

### 2. 列表要保留共同标题

销售 SOP 里的多个动作共享“下一步动作模板”这个标题。

如果必须拆成多个 Chunk，每个子块都应该补上标题路径：

```text
线索评估与跟进 SOP > 下一步动作模板

需求明确：准备对应产品材料或演示，确认决策链和测试标准。
```

### 3. 表格不要直接按字符切

表格最容易被切坏。

例如：

| 状态 | 含义 | 推荐动作 |
| --- | --- | --- |
| NEW | 尚未完成首次有效联系 | 一个工作日内完成首次触达 |
| QUALIFIED | 已达到有效线索标准 | 准备方案并确认决策链 |

如果列名和数据行被拆到不同 Chunk，模型只看到 `QUALIFIED` 和一段描述，很可能不知道每一列代表什么。

一种实用方法是把每一行转换成带字段名的文本：

```text
线索状态：QUALIFIED
状态含义：需求、角色、预算或时间计划已达到有效线索标准
推荐动作：准备对应方案，并确认决策链和测试标准
```

同时保留原始表格用于最终展示和引用。

### 4. FAQ 的问题和答案不能拆开

下面两段必须作为一个整体：

```text
问题：系统是否支持私有化部署？
答案：支持，可根据客户环境提供对应的部署方案。
```

如果把问题和答案分别向量化，搜索时可能只找到问题，没有答案。

### 5. 代码块和配置块要保持完整

配置项、SQL 和代码示例最好按完整代码块保存，不能按照自然语言标点切分。

否则返回的代码可能缺少开头、结尾或关键字段，既无法执行，也容易误导使用者。

## 七、父子分片：检索时要小，回答时要完整

结构感知切分之后，仍然会遇到一个矛盾：

- 小 Chunk 更容易精确匹配；
- 大 Chunk 更容易保留完整上下文。

父子分片可以同时满足这两个需求。

例如：

```text
父分片：线索评分参考
├── 子分片 1：需求明确
├── 子分片 2：关键角色
├── 子分片 3：时间计划
├── 子分片 4：预算信息
└── 子分片 5：信息不足
```

入库时：

- 父分片保存完整章节；
- 子分片保存更具体的规则；
- 子分片记录 `parentChunkId`；
- 通常对子分片生成向量并执行检索。

查询时：

```text
用子分片做相似度检索
  → 找到“信息不足”规则
  → 根据 parentChunkId 回到“线索评分参考”
  → 把完整章节交给大模型
```

这种方式也叫 Small-to-Big Retrieval：用小块寻找答案，用大块恢复上下文。

它非常适合产品说明、销售 SOP、合同条款和实施手册。

## 八、切分后的文本是如何向量化的

文档切分完成后，下一步就是 Embedding。

Embedding 可以理解为：把一段文本转换成一串能够表达语义的数字。

例如：

```text
“客户存在三个月以内的采购计划，可以提高线索优先级”
```

经过 Embedding 模型后，会得到类似下面的向量：

```text
[0.013, -0.082, 0.174, ..., -0.021]
```

真实向量可能包含几百到几千个数字。人不需要理解每一个数字的含义，只需要知道：语义越接近的文本，其向量在空间中的距离通常越近。

例如下面两个句子的用词不同：

```text
文档：客户存在三个月以内的选型计划，可以提高线索优先级。
问题：近期准备采购的客户是不是应该优先跟进？
```

关键词没有完全一致，但语义接近，向量检索就有机会把它们匹配起来。

### 项目中的向量化流程

当前 CRM 项目会遍历切分后的 Chunk：

```text
读取 Chunk 正文
  → 调用 Embedding 接口
  → 得到向量和向量维度
  → 保存 Chunk 元数据到 PostgreSQL
  → 保存可检索文本到 Elasticsearch
  → 保存向量和 Metadata 到 Milvus
```

Embedding 客户端采用兼容 `/embeddings` 的接口，默认模型配置为：

```properties
crm.knowledge.embedding.model=bge-m3:latest
```

请求结构可以简化为：

```json
{
  "model": "bge-m3:latest",
  "input": "需要向量化的分片文本"
}
```

Milvus 中使用 `COSINE` 作为距离类型，并同时保存：

- `tenant_id`
- `document_id`
- `document_version_id`
- `index_generation_id`
- `chunk_id`
- 标题、分类和来源
- Chunk 正文
- Embedding 向量

用户查询时，问题也必须使用同一个 Embedding 模型向量化：

```text
问题文本
  → 同一个 Embedding 模型
  → Query Vector
  → 在 Milvus 中计算余弦相似度
```

这里有一个非常重要的原则：

> 文档向量和查询向量必须来自兼容的 Embedding 模型和版本。

如果文档使用模型 A 生成向量，查询却使用模型 B，两个模型的向量空间不同，即使维度碰巧一样，也不能直接比较。

因此，更换 Embedding 模型时通常需要重建整套向量索引。

当前项目已经通过 `embeddingModel`、`vectorDimension`、`indexGenerationId` 和构建指纹记录这些信息，为后续蓝绿索引重建提供基础。

## 九、向量化时，应该使用原文还是增强后的文本

这是一个很实用的问题。

如果只向量化 Chunk 原文，标题信息可能丢失；如果把太多 Metadata 全部拼进去，又可能污染正文语义。

比较推荐的做法，是把“展示内容”和“向量化内容”分开。

例如：

```text
content：
客户存在三个月以内的选型、测试或采购计划，可提高优先级。

embeddingText：
文档：线索评估与跟进 SOP
章节：线索评分参考 > 时间计划
分类：销售流程
内容：客户存在三个月以内的选型、测试或采购计划，可提高优先级。
```

其中：

- `content` 用于最终展示和提供给大模型；
- `embeddingText` 只用于生成向量；
- `sectionPath`、分类和来源继续作为独立 Metadata 保存；
- 不要把租户编号、数据库主键等无语义字段拼入 Embedding 文本。

对应的数据结构可以设计为：

```java
public class KnowledgeChunkCandidate {

    private Integer chunkIndex;

    private String parentChunkId;

    private String sectionPath;

    private String content;

    private String embeddingText;

    private Integer tokenEstimate;
}
```

这样后续即使调整向量化文本，也不需要修改展示给用户的原始内容。

## 十、不要只存向量，Metadata 同样重要

有些 RAG 示例只往向量数据库保存两个字段：

```text
id + vector
```

实际项目远远不够。

在 CRM 场景中，至少需要知道：

- 这个 Chunk 属于哪个租户；
- 属于哪一份文档；
- 属于文档的哪个版本；
- 属于哪一代索引；
- 位于哪个章节；
- 文档分类和来源是什么；
- 当前用户是否有权限访问；
- 这个 Chunk 是否已经被删除；
- 是否仍是活动版本。

当前项目为每个 Chunk 保存了文档、版本、索引代次、标题、分类、来源、位置和构建指纹等信息。

查询完成后，系统还会回到数据库进行二次校验：

```text
租户是否一致
文档是否已删除
Chunk 是否属于活动索引代次
Chunk 是否属于文档活动版本
```

这一步虽然增加了一些查询成本，却能避免旧版本、删除数据和其他租户的数据进入大模型上下文。

生产环境中，安全性比少几毫秒延迟更重要。

---

## 十一、适合当前项目的切分升级方案

结合当前实现，可以分三步升级，不需要一次性重写全部代码。

### 第一阶段：保留现有方案，增加调试能力

先不改切分算法，只增加一个“分片预览”功能，展示：

- Chunk 序号；
- 字符数和 Token 估算；
- 开头和结尾内容；
- 相邻分片的重叠部分；
- 标题、分类和来源；
- Embedding 模型和维度；
- 是否成功写入 Elasticsearch 和 Milvus。

很多切分问题，只要把分片真正展示出来，就能立刻发现。

### 第二阶段：增加 Markdown 结构感知

当前测试知识大多是 Markdown，非常适合先支持：

- `#` 到 `######` 标题；
- 普通段落；
- 有序和无序列表；
- 表格；
- 引用块；
- 代码块。

先按结构拆分，再使用现有的 `900 + 120` 规则处理过大的结构块。

也就是说，固定长度切分不需要删除，而是从“第一层切分方式”变成“大段落的兜底切分方式”。

### 第三阶段：加入父子分片和独立 embeddingText

在 Chunk 模型中增加：

```text
parent_chunk_id
section_path
chunk_type
embedding_text_hash
splitter_version
```

检索使用子分片，生成答案时根据需要扩展父分片和相邻分片。

同时把分片策略版本加入构建指纹。只要下面任意一项变化，就创建新的索引代次：

- 最大 Chunk 长度；
- Overlap；
- 标题拼接规则；
- 父子分片规则；
- 表格转换规则；
- Embedding 模型或维度。

这样可以避免新旧切分策略生成的数据混在同一套索引中。

## 十二、如何判断切分效果是否真的变好

只看 Chunk 是否“整齐”是不够的，最终还是要看检索结果。

可以从当前 CRM 的四份测试知识开始，准备一小批固定问题：

```text
什么情况下不建议直接把线索转成客户？
完成产品演示后，销售下一步应该做什么？
系统如何保障客户数据安全？
客户认为价格高时应该如何处理？
知识库没有记录某个价格时，系统应该怎么回答？
```

每个问题人工标记正确的文档和 Chunk，然后分别测试不同切分方案。

建议先比较：

| 实验 | 切分方案 | 重点观察 |
| --- | --- | --- |
| A | 500 + 80 | 是否更精准，是否丢失上下文 |
| B | 900 + 120 | 当前基线 |
| C | 1500 + 200 | 是否带入过多无关内容 |
| D | 结构感知切分 | 标题、列表和表格是否更完整 |
| E | 父子分片 | 精确召回后能否恢复完整章节 |

至少记录下面几个指标：

- `Recall@5`：正确 Chunk 是否出现在前 5 个结果中；
- `MRR@10`：第一个正确 Chunk 排在多靠前的位置；
- 上下文 Token 数：最终交给大模型的内容有多长；
- 重复率：TopK 中是否存在大量重复分片；
- 答案忠实度：最终回答是否完全来自检索证据；
- 无答案误召回率：知识库没答案时是否仍然硬找资料。

最重要的是，每次实验只修改一个变量。

不要同时更换 Embedding 模型、Chunk 大小、Overlap、TopK 和 Prompt，否则即使结果变好了，也不知道是哪一项修改带来的收益。

---

## 十三、几个常见误区

### 误区一：Chunk 越小越精准

小 Chunk 会让主题更集中，但也可能失去标题、前提和上下文。

### 误区二：Overlap 越大越保险

Overlap 过大会制造大量重复内容，让 TopK 看上去有很多结果，实际上都在说同一件事。

### 误区三：换一个更强的 Embedding 模型就能解决问题

如果文档在切分时已经把问题和答案拆开，再强的 Embedding 模型也无法恢复不存在的上下文。

### 误区四：只要写入向量数据库就完成了

企业 RAG 还需要保存租户、权限、文档版本、索引代次、来源和删除状态。

### 误区五：根据一两个问题判断效果

同一个参数可能让 FAQ 变好，却让表格和长文档变差。必须使用固定问题集评测。

### 误区六：更换模型后继续复用旧向量

不同 Embedding 模型的向量通常不在同一个空间。更换模型后，需要重新生成文档向量，并通过新索引代次安全切换。

## 十四、上线前检查清单

文档处理：

- [ ] 是否清理了页眉、页脚、目录和重复内容？
- [ ] Markdown、表格、列表和代码块是否保持完整？
- [ ] 标题是否与正文一起参与向量化？
- [ ] FAQ 的问题和答案是否在同一语义块中？

Chunk 设计：

- [ ] Chunk 是否过小或过大？
- [ ] Overlap 是否造成大量重复结果？
- [ ] 是否保存章节路径和 Chunk 类型？
- [ ] 是否需要父子分片？
- [ ] 切分策略是否具有明确版本？

向量化：

- [ ] 文档与查询是否使用同一 Embedding 模型？
- [ ] 是否记录模型名称和向量维度？
- [ ] 更换模型后是否重建索引？
- [ ] 是否区分展示内容与 embeddingText？

安全与版本：

- [ ] 是否携带租户和权限 Metadata？
- [ ] 是否校验活动文档版本？
- [ ] 是否校验活动索引代次？
- [ ] 文档删除后，ES 和 Milvus 数据是否同步清理？

评测：

- [ ] 是否准备了固定问题集？
- [ ] 是否记录 Recall、MRR、重复率和 Token 数？
- [ ] 是否包含无答案和越权问题？
- [ ] 每次实验是否只修改一个变量？

## 总结

RAG 文档切分不是简单地“每 900 个字符切一刀”。

一套比较可靠的切分方案，至少需要考虑：

```text
文档清洗
+ 结构识别
+ 语义边界
+ Chunk 大小
+ Overlap
+ 标题路径
+ 父子分片
+ Metadata
+ 切分策略版本
```

向量化也不只是调用一次 Embedding 接口。我们还要保证文档和查询使用同一模型，保存模型版本和向量维度，并在策略或模型变化后安全重建索引。

对于当前 CRM 项目，`900 + 120` 的自然边界切分已经是一套稳定的基础方案。下一步最值得做的不是马上更换模型，而是增加分片预览、Markdown 结构感知、父子分片和固定评测集。

只有把进入知识库的每一个 Chunk 做好，后面的混合检索、Reranker 和大模型回答才有优化空间。
